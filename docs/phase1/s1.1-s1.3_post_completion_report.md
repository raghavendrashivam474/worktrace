## 1. Executive Summary

The three sprints covered by this report convert the existing Tasks destination from a placeholder screen into a functional, offline-first task management workflow backed by Drift/SQLite and integrated into the existing Worktrace application shell.

A user can now:

- Open the application and navigate to Tasks using the existing shell
- See an empty state when no tasks exist
- Create a task via a dialog with validated title input
- See the saved task in the list
- Toggle completion with visual distinction (strikethrough)
- Delete a task via confirmation dialog
- Close and reopen the application without losing data
- Receive feedback for invalid input and loading/error states

The implementation preserves the Phase 0 architecture entirely: the app shell, navigation, theming, design system, and existing tests are untouched except where tests had to adapt to the new TasksScreen behavior.

**Verification:** 50 tests passing, 0 static analysis issues, formatting clean. Android debug build and GitHub Actions CI are deferred to the pre-merge checklist.

**Phase 1 remains incomplete.** S1.4 (task organization — filters, sorting) and S1.5 (reliability & recovery — hardened validation, additional persistence tests, polished error handling) have not been started. The brief explicitly scoped only S1.1–S1.3.

## 3. Architecture Implemented

### 3.1 Directory structure additions

```
lib/
  core/
    data/
      app_database.dart              # Drift database (shared across features)
      app_database.g.dart            # Generated Drift output (committed, DEC-013)
      database_provider.dart         # Riverpod provider + openDatabase()
  features/
    tasks/
      domain/
        task.dart                    # Plain Dart model (DEC-012)
        task_repository.dart         # Abstract contract
      data/
        tasks_table.dart             # Drift table definition
        task_repository_impl.dart    # Drift-backed implementation
        task_repository_provider.dart # Riverpod provider
      presentation/
        task_list_provider.dart      # AsyncNotifier
      tasks_screen.dart              # Rewritten from placeholder

test/
  features/
    tasks/
      domain/task_test.dart
      data/task_repository_test.dart
      presentation/task_list_provider_test.dart
      tasks_screen_test.dart
```

The structure extends DEC-011 (feature-first) by introducing `lib/core/data/` for cross-feature infrastructure (the shared database). This was documented as DEC-015.

### 3.2 Layering

```
Widget (TasksScreen, ConsumerWidget)
    │
    ▼
AsyncNotifier (TaskListNotifier)         ← application logic
    │
    ▼
TaskRepository (abstract)                 ← domain contract
    │
    ▼
DriftTaskRepository (impl)                ← persistence
    │
    ▼
AppDatabase (Drift) → SQLite (file / in-memory)
```

No layer below the application logic depends on Flutter widgets. No layer above the repository depends on Drift types. This preserves the clean domain/data separation required by DEC-012 and keeps the sync-readiness path open.

### 3.3 Dependency injection

Riverpod providers compose the graph:

- `databaseProvider` — throws `UnimplementedError` by default; must be overridden in `ProviderScope`
- `taskRepositoryProvider` — reads `databaseProvider`, returns `DriftTaskRepository`
- `taskListProvider` — `AsyncNotifierProvider`, depends on `taskRepositoryProvider`

The throwing default is deliberate: it fails loudly in tests and development if the database wiring is missing, instead of silently returning null.

## 4. Implementation Details

### 4.1 Task domain model (`lib/features/tasks/domain/task.dart`)

Plain Dart class with factory validation:

```dart
factory Task.create({ required String id, required String title, DateTime? createdAt }) {
  final normalized = title.trim();
  if (normalized.isEmpty) {
    throw ArgumentError.value(title, 'title', 'must not be empty or whitespace-only');
  }
  // ...
}
```

Rules enforced:

1. Title trimmed and non-empty
2. `createdAt` immutable; defaults to `DateTime.now()`
3. `updatedAt` refreshed on every mutation (`toggleCompletion`, `updateTitle`)
4. Equality by `id` only (DEC-014: UUIDs are the identity)
5. `updateTitle` re-validates

### 4.2 Persistence (`DriftTaskRepository`)

The Drift generated class is named `TaskRow` via `@DataClassName('TaskRow')` to avoid colliding with the domain `Task`. The repository maps between them in a private `_toDomain(TaskRow)` helper.

The public API accepts and returns only domain `Task` objects. No Drift companion types or query builders are exposed.

Default ordering is `createdAt DESC` (newest first), applied in both `getAllTasks()` and `watchAllTasks()`.

### 4.3 Application state (`TaskListNotifier`)

```dart
class TaskListNotifier extends AsyncNotifier<List<Task>> {
  @override
  Future<List<Task>> build() => _repo.getAllTasks();

  Future<void> createTask(String title) async {
    final task = Task.create(id: const Uuid().v4(), title: title);
    await _repo.createTask(task);
    await _reload();
  }
  // toggleTask, deleteTask, _reload...
}
```

After every mutation the list is reloaded from the repository via `AsyncValue.guard`. This is the simplest correct approach for a small feature. A reactive `.watch()` stream subscription was considered but deferred to avoid introducing additional complexity that is not yet required.

### 4.4 UI (`TasksScreen`)

A `ConsumerWidget` that renders based on `AsyncValue`:

- `loading` → `CircularProgressIndicator`
- `error` → error icon + message + Retry button (invalidates the provider)
- `data` with empty list → `WtEmptyState` (reused Phase 0 primitive) with create prompt
- `data` with tasks → `ListView.builder` of `_TaskListItem`

Each `_TaskListItem` has:
- `Checkbox` for toggle
- Strikethrough + muted color when completed
- Delete `IconButton` with confirmation dialog

The create flow uses an `AlertDialog` with `TextField`, inline validation (`errorText`), and `Cancel` / `Create` actions. Validation is enforced both before `pop(true)` (dialog stays open on invalid input) and defensively in the notifier (which also throws `ArgumentError`).

### 4.5 Database initialization

```dart
void main() async {
  WidgetsFlutterBinding.ensureInitialized();
  final db = await openDatabase();
  runApp(ProviderScope(
    overrides: [databaseProvider.overrideWithValue(db)],
    child: const WorktraceApp(),
  ));
}
```

`openDatabase()` resolves the application documents directory via `path_provider` and opens `worktrace.db`. The schema is version 1; `MigrationStrategy.onCreate` runs `m.createAll()` on first launch.

## 7. Problems Encountered and Resolutions

This is the section the senior developer should read most carefully. All issues were resolved before this report was written, but each represents a real engineering risk worth noting.

### 7.1 Drift `TasksCompanion.insert` argument type mismatch

**Symptom:**  
```
Error: The argument type 'bool' can't be assigned to the parameter type 'Value<bool>'.
```

**Cause:**  
The `isCompleted` column has a default via `.withDefault(const Constant(false))`, which makes it an optional (nullable) parameter on the companion. Optional companion parameters require a `Value<T>` wrapper, not a raw value.

**Resolution:**  
Changed `isCompleted: task.isCompleted` to `isCompleted: Value(task.isCompleted)` in the insert call. Required columns do not need the wrapper; defaulted columns do.

**Lesson:**  
When adding `.withDefault(...)` to a Drift column, remember that the generated companion parameter becomes `Value<T>`, not `T`.

### 7.2 `isNull` / `isNotNull` ambiguous import

**Symptom:**  
```
Error: 'isNotNull' is imported from both
'package:drift/src/runtime/query_builder/query_builder.dart' and
'package:matcher/src/core_matchers.dart'.
```

**Cause:**  
Drift exports `isNull` and `isNotNull` as SQL expression helpers. The `matcher` package (via `flutter_test`) also exports them as test matchers. In a test file that imports both, Dart cannot disambiguate.

**Resolution:**  
Changed the Drift import in the test file to `import 'package:drift/drift.dart' hide isNull, isNotNull;`. Later, when only `driftRuntimeOptions` was actually needed from drift, this was tightened further to `show driftRuntimeOptions`.

**Lesson:**  
Prefer `show` over `hide` when you only need a small symbol from a large library — it is more explicit and more defensive against future name collisions.

### 7.3 Flaky `updatedAt` timing assertion

**Symptom:**  
```
Task.toggleCompletion toggles from incomplete to complete [E]
  Expected: not DateTime:<2026-10-19 04:31:21.708652>
    Actual: DateTime:<2026-10-19 04:31:21.708652>
```

**Cause:**  
A test asserted that `toggled.updatedAt` was not equal to `task.updatedAt`. In practice, both `DateTime.now()` calls happened within the same microsecond on a fast machine, producing identical timestamps.

**Resolution:**  
Removed the timing assertion from the domain test. The behavior "updatedAt refreshes on mutation" is still implicitly covered by the persistence tests, which use fixed `createdAt` values and verify that `createdAt` is preserved across updates.

**Lesson:**  
Avoid real-clock equality / inequality assertions. If a test needs to verify "updatedAt changed", inject a clock or compare against a captured timestamp with a tolerance.

### 7.4 SQLite DateTime microsecond truncation

**Symptom:**  
```
Expected: DateTime:<2026-10-19 04:32:54.713809>
  Actual: DateTime:<2026-10-19 04:32:54.000>
```

**Cause:**  
Drift serializes `DateTime` as Unix epoch seconds (integer) by default, which drops sub-second precision. A test that inserted `DateTime.now()` and then compared the stored value against the original always failed.

**Resolution:**  
Used `DateTime(2026, 6, 15, 12, 0, 0)` in the test — a value with no sub-second component — so the round-trip is lossless.

**Lesson:**  
Drift's default DateTime storage is second-precision. If millisecond or finer precision is needed later, switch to `storeDateTimeAsText: true` in the `@DriftDatabase` options or convert to `int` milliseconds explicitly. Phase 1 does not need this; it should be revisited if timestamps become user-visible with high precision.

### 7.5 SQLite DateTime timezone round-trip

**Symptom:**  
```
Expected: DateTime:<2026-06-15 12:00:00.000Z>
  Actual: DateTime:<2026-06-15 17:30:00.000>
```

**Cause:**  
After switching the test to use `DateTime.utc(...)`, Drift stored the UTC value but reconstructed it as a local `DateTime`. On a developer machine in IST (UTC+5:30), `12:00 UTC` came back as `17:30` local time. Dart treats these as unequal because their `.isUtc` flags differ.

**Resolution:**  
Changed the fixture to `DateTime(2026, 6, 15, 12, 0, 0)` — a local `DateTime`. The round-trip then preserved both the value and the local flag.

**Lesson:**  
Drift's default DateTime handling is local-time. If the application needs UTC semantics, that choice must be explicit at the schema level, not left to individual callers.

### 7.6 Drift "multiple databases" warning in the reconnection test

**Symptom:**  
```
WARNING (drift): It looks like you've created the database class AppDatabase
multiple times. When these two databases use the same QueryExecutor,
race conditions will occur and might corrupt the database.
```

**Cause:**  
The reconnection test deliberately opens the same database file twice (close, then reopen) to prove persistence survives. Drift's debug diagnostics flagged this as suspicious.

**Resolution:**  
Set `driftRuntimeOptions.dontWarnAboutMultipleDatabases = true` for the duration of that test only, with an `addTearDown` to restore the default. The behavior being tested is intentional and the two instances never coexist.

**Lesson:**  
Drift's warning is correct in normal application code (never open the same file twice concurrently). In targeted persistence tests the warning can be scoped off, but the suppression must be local to the test, not global.

### 7.7 Unused imports after refactoring

**Symptom:**  
`unused_import` analysis warnings for `dart:io` in `app_database.dart` and `package:drift/drift.dart` in a test file after the `hide` directive was tightened.

**Resolution:**  
Removed both imports. Clean static analysis is a mandatory gate per DEC-013.

**Lesson:**  
After every refactor, run `flutter analyze` before claiming success. Unused imports are the most common post-refactor issue.

### 7.8 Widget tests crashing with "widget inspector unsafe lookup" cascades

**Symptom:**  
Multiple widget tests failed with large stack traces including:
```
Looking up a deactivated widget's ancestor is unsafe.
Tried to build dirty widget in the wrong build scope.
A TextEditingController was used after being disposed.
```

**Cause (two independent bugs):**

1. The create dialog disposed its `TextEditingController` immediately after `showDialog` returned. The dialog's exit animation then rebuilt internal widgets (`AnimatedDefaultTextStyle`, `_FocusInheritedScope`) that still referenced the controller, triggering the use-after-dispose assertion. The resulting cascade of "deactivated widget" errors obscured the actual root cause for a while.

2. `pumpAndSettle()` alone was not sufficient to settle the combination of a closing Material dialog and an async Riverpod `_reload()` call. The test observed the state at an intermediate frame where the created task had been persisted in the fake repo but the `AsyncNotifier` had not yet rebuilt.

**Resolution:**

1. Replaced the immediate `controller.dispose()` with `Future.delayed(const Duration(milliseconds: 300), controller.dispose)` to wait past the dialog exit animation. 300 ms matches the Material dialog transition duration.

2. Introduced a `settleAfterDialog(tester)` test helper that performs `pump() → pump(500 ms) → pumpAndSettle()` to allow both the dialog exit and the subsequent async notifier rebuild to complete before assertions.

**Lesson:**  
Dialog lifecycle in Flutter is not instantaneous. Any resource owned by the caller (controllers, subscriptions, focus nodes) must outlive the dialog's exit animation. In tests, async state updates that originate after the dialog closes require explicit extra pumps — `pumpAndSettle` is not a guarantee that cross-boundary async work is complete.

### 7.9 Existing navigation tests broken by the new TasksScreen

**Symptom:**  
Three tests in `test/navigation_test.dart` failed:
```
Expected: exactly one matching candidate
  Actual: Found 0 widgets with text "Task management will be available in a future update."
```

**Cause:**  
These tests were written in Phase 0 against the placeholder `TasksScreen`. The new screen is a `ConsumerWidget` that requires a working `taskRepositoryProvider`. Without an override, the default `databaseProvider` throws `UnimplementedError`, which causes `TasksScreen` to render its error state. Additionally, the old placeholder text no longer exists.

**Resolution:**  
Updated the navigation test file to:
- Define a minimal `_FakeTaskRepo` that returns an empty list
- Wrap `WorktraceApp` in a `ProviderScope` that overrides `taskRepositoryProvider` with the fake
- Replace assertions on the old placeholder text with assertions on the new empty-state text (`"No tasks yet"`)

The navigation test file is the only test that was modified to accommodate the new screen; it was not weakened. All original scenarios (initial state, tab navigation, repeated taps, back navigation, responsive layouts) still assert the same behaviors.

**Lesson:**  
Changing a screen from a `StatelessWidget` to a `ConsumerWidget` is a breaking change for any widget test that pumps that screen without providing the necessary Riverpod graph. Audit existing widget tests whenever a feature screen gains new provider dependencies.

### 7.10 PowerShell encoding of files

**Symptom (minor):**  
Early scripts wrote files that could have introduced BOMs or mangled em-dashes in the generated Dart source.

**Resolution:**  
All file writes used `[System.IO.File]::WriteAllText` with a `New-Object System.Text.UTF8Encoding $false` (no-BOM) encoder, and all string literals were kept to plain ASCII where possible. No encoding issues made it into the committed files; `flutter analyze` and `dart format` passed on every generated file.

**Lesson:**  
On Windows, prefer explicit `UTF8Encoding $false` when generating source files from PowerShell. The default `Set-Content` / `Out-File` cmdlets may introduce BOMs that cause subtle issues in some tools.
