## 3. S3.4.A — Transactional Import

### 3.1 Problem Identified

Inspection of `lib/features/portability/data/portability_service.dart` revealed that `importWorkspace()` performed per-record writes with individual try/catch blocks that silently swallowed failures:

```dart
// Original pattern (unsafe)
for (final t in export.tasks) {
  final existing = await _taskRepo.getTaskById(t.id);
  if (existing != null) { tasksSkipped++; continue; }
  try {
    await _taskRepo.createTask(...);
    tasksImported++;
  } catch (e) {
    tasksSkipped++;
    errors.add('Task "${t.id}": $e');
  }
}
```

This meant a failure on record N left records 1 through N−1 persisted. The result object could falsely report "partial success," and the user's database would be left in an inconsistent state with no recovery path. This is the single highest-risk issue in the Phase 3 codebase because import mutates persistent user data.

### 3.2 Solution Design

Repository wiring was inspected to determine whether a single transaction boundary was feasible. All three repositories (`DriftTaskRepository`, `DriftSnippetRepository`, `DriftTaskSnippetLinkRepository`) are constructed with the same `AppDatabase` instance via `databaseProvider`. In Drift, calling `db.transaction(() async { ... })` makes **all operations on that `db` instance** within the closure participate in a single SQLite transaction, including operations routed through repository methods that use the same `db`.

This meant the fix was surgical and required no architectural change:

1. Add `AppDatabase _db` to `PortabilityService` constructor.
2. Wrap the import body in `await _db.transaction(() async { ... })`.
3. Remove per-record try/catch so failures propagate to the transaction boundary and trigger a rollback.
4. Remove the `errors` list from `ImportResult` (atomic transactions either succeed completely or throw — there are no partial failures to report).

**No ADR raised.** No repository contracts changed. No schema changes. The transaction boundary is an internal implementation detail of the service.

### 3.3 Implementation Changes

**`lib/features/portability/data/portability_service.dart`** — rewritten:

- Constructor now accepts `AppDatabase db` via initializing formal (`required this._db`).
- `importWorkspace()` body wrapped in `_db.transaction(() async { ... })`.
- Per-record error swallowing removed. On any persistence failure, the entire transaction rolls back and the exception propagates to the caller.
- `validateExport()` remains outside the transaction — it is pure parsing with no database access, so invalid files are rejected before any mutation.

**`lib/features/portability/data/portability_service_provider.dart`** — updated:

```dart
final portabilityServiceProvider = Provider<PortabilityService>((ref) {
  return PortabilityService(
    taskRepo: ref.watch(taskRepositoryProvider),
    snippetRepo: ref.watch(snippetRepositoryProvider),
    linkRepo: ref.watch(taskSnippetLinkRepositoryProvider),
    db: ref.watch(databaseProvider),  // added
  );
});
```

**`lib/features/portability/presentation/portability_section.dart`** — pre-existing bug fixed:

The original code called `service.validateExport(json)` without a try/catch wrapping it. A malformed file would therefore crash the import flow with an unhandled `FormatException` instead of showing a user-friendly error. The try/catch at the import step now covers transaction failures as well, and the user-facing message was reworded to say *"Import failed. No data was changed."* (truthful because of the rollback guarantee).

### 3.4 Rollback Tests — Design and Problems Faced

The brief explicitly required: *"At least one rollback test must simulate a real database operation failure inside the import transaction. A test that fails only during JSON validation does not prove transactional rollback."*

To meet this requirement, the tests use **real SQLite `RAISE(ABORT)` triggers** that fire inside the transaction on specific inserts. This causes a genuine database-level failure that must be rolled back by SQLite itself — not simulated via a mock.

**First attempt (failed):** The initial implementation tried to install the trigger via `NativeDatabase.memory(setup: (rawDb) => rawDb.execute(...))`. All three rollback tests failed with:

```
SqliteException(1): no such table: main.snippets
```

**Root cause analysis:** The `setup` callback in `NativeDatabase.memory` runs **before** Drift creates the application schema. The `snippets` table did not yet exist when the trigger definition referenced it.

**Mitigation:** A helper function `createDbWithSnippetTrigger()` was introduced:

```dart
Future<AppDatabase> createDbWithSnippetTrigger(String failSnippetId) async {
  final testDb = AppDatabase(NativeDatabase.memory());
  // Force Drift to create all tables by running a trivial query.
  await testDb.customSelect('SELECT 1').get();
  // Now the snippets table exists — install the trigger.
  await testDb.customStatement('''
    CREATE TRIGGER fail_on_specific_snippet
    BEFORE INSERT ON snippets
    WHEN NEW.id = '$failSnippetId'
    BEGIN
      SELECT RAISE(ABORT, 'Simulated DB failure');
    END;
  ''');
  return testDb;
}
```

The `SELECT 1` forces Drift to lazily initialize the schema; after that, the trigger can be safely installed via `customStatement`. All three rollback tests then passed.

## 4. S3.4.B — Real v2 → v3 Migration Replay

### 4.1 Problem Identified

The Phase 3 report acknowledged that no complete migration replay from a real version 2 database existed. The existing migration tests only verified schema version assertions and v1→v2 behavior. A fresh-start test that creates a v3 database and asserts `schemaVersion == 3` does not prove that existing user data upgrades safely.

### 4.2 Solution Design

The existing v1→v2 test in `test/features/snippets/data/migration_test.dart` was extended with a new `group('database migration v2 -> v3')` containing a single comprehensive test that:

1. Creates a fresh temporary file-based SQLite database.
2. Constructs a **real v2 schema** using raw `sqlite3` — tasks and snippets tables only, no links table.
3. Inserts representative data (2 tasks including one completed, 2 snippets with different languages) using Drift's DateTime encoding (seconds-since-epoch INTEGER).
4. Sets `PRAGMA user_version = 2`.
5. Closes the raw connection cleanly.
6. Opens the database through the production `AppDatabase(NativeDatabase(File(dbPath)))` path, which executes the real `onUpgrade` migration.
7. Verifies all pre-existing data survives with correct fields and timestamps.
8. Verifies the new `task_snippet_links` table exists and accepts valid associations.
9. Verifies FK cascade behavior in both directions.
10. Verifies duplicate `(taskId, snippetId)` prevention via composite primary key.
11. Verifies dangling FK references are rejected by foreign-key enforcement.
12. Verifies the database operates normally after migration (new entity creation).

**No historical migrations were modified.** The test uses the actual production `MigrationStrategy` defined in `app_database.dart`.

### 4.3 Test Execution

The test passed on first run. No problems were encountered. Combined with the existing v1→v2 and fresh-database tests, the migration suite now proves the full upgrade path from v1 through v3.
