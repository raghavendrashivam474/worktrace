## 2. Approach

### 2.1 Inspection Before Implementation

Following Section 3 of the brief, I began with a strictly read-only inspection phase. I read every file in `lib/`, `test/`, and `docs/` relevant to the Task capability, the application shell, the database layer, and the existing architectural decisions (DEC-001 through DEC-020).

The purpose was to answer four concrete questions before writing any code:

1. Where exactly are Task domain rules defined, and are they independent of Flutter and Drift?
2. What does the existing repository contract expose, and how does the Drift implementation map between domain and database types?
3. How does Riverpod wire the database into the widget tree?
4. How are migrations handled, and what test facilities already exist?

The answers were unambiguous. The existing codebase follows a clean feature-first structure (DEC-011) with plain Dart domain models (DEC-012), abstract repository contracts, Drift-backed implementations isolated to the data layer, and `AsyncNotifierProvider`-based state management. The Task capability was, in effect, a complete reference implementation for how the Snippet capability should be built.

This inspection yielded S2.1's primary deliverable: `docs/phase2/s2.1_architecture_audit.md`.

### 2.2 Decision to Mirror, Not Reinvent

Because the Task capability satisfies all seven capability-isolation principles listed in Section 4.1.D of the brief, I made a conscious decision - documented in the S2.1 audit - not to propose any architectural changes. Introducing new abstractions (service locators, event buses, generic repository factories, or capability registries) would have violated Section 1 of the brief, which explicitly warns against unnecessary abstraction.

Instead, the Snippet implementation mirrors the Task implementation structurally:

| Task Layer | Snippet Equivalent |
|---|---|
| `Task` (plain Dart with `factory create()`) | `Snippet` (same pattern) |
| `TaskRepository` (abstract) | `SnippetRepository` (abstract) |
| `DriftTaskRepository implements TaskRepository` | `DriftSnippetRepository implements SnippetRepository` |
| `Tasks` Drift table with `@DataClassName('TaskRow')` | `Snippets` with `@DataClassName('SnippetRow')` |
| `taskRepositoryProvider` | `snippetRepositoryProvider` |
| `TaskListNotifier extends AsyncNotifier<List<Task>>` | `SnippetListNotifier extends AsyncNotifier<List<Snippet>>` |
| `FakeTaskRepository` (test fixture) | `FakeSnippetRepository` (test fixture) |

This decision was recorded in the audit before any Snippet code was written.

### 2.3 Incremental Verification

Rather than deferring all testing until S2.4, I verified every sprint boundary independently per Section 8 of the brief. After each code block, I ran `dart format`, `flutter analyze`, and `flutter test`. This caught issues early and kept the diff reviewable.

**Schema change:**

```dart
@DriftDatabase(tables: [Tasks, Snippets])
class AppDatabase extends _$AppDatabase {
  @override
  int get schemaVersion => 2;

  @override
  MigrationStrategy get migration => MigrationStrategy(
        onCreate: (Migrator m) => m.createAll(),
        onUpgrade: (Migrator m, int from, int to) async {
          if (from < 2) {
            await m.createTable(snippets);
          }
        },
      );
}
```

The migration is strictly additive. The `tasks` table definition and all existing Task data are untouched.

**Repository implementation details:**

- Mapping between `Snippet` and `SnippetRow` is centralized in a private `_toDomain(SnippetRow)` method.
- No Drift types (`SnippetRow`, `SnippetsCompanion`, `OrderingTerm`) are exposed through the public interface.
- `getAllSnippets` and `watchAllSnippets` order by `createdAt DESC` to match Task behavior.

## 4. Problems Encountered and Mitigations

### 4.1 Problem: Corrupted UTF-8 Comment Characters in Existing Test File

**Detected during:** S2.1 inspection.

**Symptom:** `test/features/tasks/tasks_screen_test.dart` contained section-divider comments where original box-drawing characters (likely `-- S1.4-A: Edit tests --`) had been double-encoded into sequences like `ÃƒÂ¢Ã¢â‚¬ÂÃ¢â€šÂ¬`.

**Impact:** Cosmetic only. The file compiled, all 76 tests passed. However, the corruption rendered the section organization unreadable in editors and risked further mangling on future saves.

**Mitigation:** Replaced the corrupted comment lines with clean ASCII dividers (`// -- S1.4-A: Edit tests --`) using a bounded regex that only matched lines starting with `//` containing recognizable section labels. Only six comment lines were modified. No code logic was altered. All 76 Task tests continued to pass after the fix.

**Risk assessment:** Low. The change is limited to comments, is diff-reviewable in under a minute, and does not require history rewriting.

### 4.2 Problem: PowerShell Terminal Mangled Unicode in Audit Document

**Detected during:** S2.1 audit creation.

**Symptom:** The audit markdown file used `[OK]` emoji for the capability-boundary assessment table. When PowerShell wrote the file via a here-string, the encoding degraded to `?` placeholders.

**Mitigation:** Replaced all `[OK]` (U+2705) occurrences with ASCII `[PASS]` using `[System.IO.File]::ReadAllText` and `[System.IO.File]::WriteAllText` with an explicit `UTF8Encoding($false)` (no BOM). This bypassed PowerShell's string coercion entirely.

**Lesson:** For all subsequent documentation writes in this sprint, I used ASCII-only characters and explicit UTF-8 file I/O rather than cmdlet-based `Set-Content`.

### 4.3 Problem: Terminal Output Truncation During Code Inspection

**Detected during:** S2.1, Block 4.

**Symptom:** When attempting to read 10+ source files in a single PowerShell block, the terminal buffer overflowed and the first two files were truncated.

**Mitigation:** Split the inspection into smaller blocks (one or two files per invocation). This is not an elegant fix but is reliable in a Windows PowerShell environment.

**Future improvement:** For a long inspection pass, consider redirecting output to a file (`Get-Content ... > inspection.log`) rather than relying on terminal scrollback.

### 4.4 Problem: `build_runner` Flag Deprecation Warning

**Detected during:** S2.4, Block 13.

**Symptom:** `dart run build_runner build --delete-conflicting-outputs` emitted a warning:
> `These options have been removed and were ignored: --delete-conflicting-outputs`

**Impact:** None. The build succeeded and generated the correct output. The newer `build_runner` version apparently deletes conflicting outputs by default.

**Mitigation:** Noted for future sprint commands. The flag can be removed in subsequent documentation. No code change needed.

### 4.5 Problem: Missing `AppDatabase.v1()` Constructor for Migration Test

**Detected during:** S2.4, Block 14.

**Symptom:** My initial migration test used `AppDatabase.v1(NativeDatabase(File(dbPath)))` to set up a v1 database state, but no such named constructor existed.

**Options considered:**

1. **Add an `AppDatabase.v1()` constructor** - would modify production code purely for testing, violating the principle of keeping test scaffolding out of production classes.
2. **Create a separate `AppDatabaseV1` class** - would duplicate the Task table definition and could drift out of sync.
3. **Use raw `sqlite3` to construct the v1 schema manually** - standard Drift migration-testing pattern; isolates test scaffolding entirely to the test file.

**Decision:** Option 3. Rationale documented in Section 7.3 of the brief, which requires using "the project's existing migration-test facilities and supported Drift test utilities" rather than inventing new structures.

**Implementation:** The migration test opens the database file with the `sqlite3` package directly, issues raw `CREATE TABLE` SQL matching the v1 schema, inserts Task rows using Drift's `DateTime` encoding (seconds since epoch as `INTEGER`), sets `PRAGMA user_version = 1`, closes the raw handle, then reopens with `AppDatabase` to trigger the `onUpgrade` callback. The test verifies both that Task data survives and that the newly-created `snippets` table is operational.

### 4.6 Problem: `sqlite3` Not a Direct Dependency

**Detected during:** S2.4, Block 15.

**Symptom:** `flutter analyze` reported:
> `The imported package 'sqlite3' isn't a dependency of the importing package.`

**Root cause:** `sqlite3` was present only as a transitive dependency through `sqlite3_flutter_libs`. The analyzer correctly flagged that the migration test should declare its own dependency.

**Mitigation:** Added `sqlite3: ^3.5.2` to `dev_dependencies` (test-only; it does not affect the production app). Verified via `flutter pub get` that no version conflict occurred - the resolved version matched the existing transitive version.

### 4.7 Problem: Deprecated `dispose()` Call on `sqlite3.Database`

**Detected during:** S2.4, Block 15.

**Symptom:** `flutter analyze` reported:
> `'dispose' is deprecated and shouldn't be used. Call close() instead.`

**Mitigation:** Replaced `rawDb.dispose()` with `rawDb.close()` in the migration test. One-line change.

### 4.8 Problem: Format Drift After Regex Replacements

**Detected during:** S2.1 cleanup and S2.4 fixes.

**Symptom:** After in-place regex replacements, `dart format --set-exit-if-changed` reported changes because the replacement text produced different line lengths than the original.

**Mitigation:** After every regex-based file modification, I ran `dart format .` to apply the project's canonical formatting, then re-ran `dart format --output=none --set-exit-if-changed .` to confirm cleanliness. This became a routine step in every subsequent block.
