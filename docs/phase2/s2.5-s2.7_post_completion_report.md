## 1. Executive Summary

Sprints S2.5 through S2.7 complete the Snippet capability for Worktrace, delivering a fully functional code snippet workspace with CRUD operations, search, filtering, sorting, and responsive layout — all without regressing the existing Task capability. The implementation reuses the domain, repository, and provider layers established in S2.1–S2.4, adding only the presentation tier and integration tests. The most significant engineering challenge was a persistent 14-pixel `RenderFlex` overflow at small viewports, traced through systematic elimination to the `DropdownButtonFormField` widget's internal `InputDecorator` constraints.

## 2. S2.5 — Snippet Workspace UI

### 2.1 What Was Implemented

The `SnippetsScreen` (`ConsumerStatefulWidget`, ~735 lines) provides the complete snippet management interface:

- **Create flow:** Modal dialog with `TextFormField` inputs for title, code (multiline, monospace), and language. All fields validated non-empty before submission. Calls `snippetListProvider.createSnippet()`.
- **Read flow:** `ListView.builder` rendering `_SnippetListItem` cards. Each card displays the snippet title (single-line, ellipsis overflow), a language tag, a two-line monospace code preview (truncated at 80 characters), and edit/delete action buttons. Tapping a card opens a detail dialog with full code display and a copy-to-clipboard action.
- **Update flow:** Edit dialog pre-populated with the snippet's current title, code, and language. Submits via `snippetListProvider.editSnippet()`.
- **Delete flow:** Confirmation dialog with destructive action styling. Calls `snippetListProvider.deleteSnippet()`.
- **Async states:** Loading (`CircularProgressIndicator`), empty (`WtEmptyState` with prompt to create), and error (retry button that invalidates the provider).
- **Navigation:** `SnippetsScreen` occupies index 2 in `AppShell`'s `IndexedStack`, accessible via `NavigationBar` (<600px) or `NavigationRail` (≥600px). No navigation changes were required — the destination was already wired in S2.1–S2.4.

### 2.2 How It Was Implemented

- **State management:** The screen watches `snippetListProvider` (an `AsyncNotifierProvider` backed by `SnippetRepository`). All mutations flow through the provider, which handles optimistic updates and re-fetching. No direct SQLite queries or Drift row types appear in the UI layer.
- **Test infrastructure:** A `FakeSnippetRepository` with a `shouldFail` flag provides instant-return test doubles for happy-path and error-path tests. A `_DelayedSnippetRepository` backed by a `Completer<List<Snippet>>` enables testing the loading state (the instant-return fake resolves too quickly for the test to observe the loading indicator). A `buildTestApp(SnippetRepository repo)` helper wraps the screen in a `ProviderScope` with the repository override.
- **Test coverage:** 13 widget tests covering create, read (list + detail), edit, delete, loading, empty, error, and layout scenarios.

### 2.3 Problems Faced and Mitigations

| Problem | Root Cause | Mitigation |
|---------|-----------|------------|
| Loading indicator test flaky | `FakeSnippetRepository` returns instantly; the future resolves before the test can observe the loading state | Created `_DelayedSnippetRepository` with a `Completer` that the test controls manually |
| `find.text('Detail Test')` ambiguous | The same text appears in both the list card and the detail dialog, causing `findsOneWidget` to fail | Used `findsWidgets` for ambiguous text and `find.text('Close')` as the definitive dialog proof |
| `buildTestApp` parameter too narrow | Typed as `FakeSnippetRepository`, but `_DelayedSnippetRepository` is a separate class | Widened parameter to `SnippetRepository` (the abstract interface) |

## 3. S2.6 — Discovery & Organization

### 3.1 What Was Implemented

Three discovery capabilities layered onto the existing snippet list:

- **Search:** A `TextField` with a search icon prefix and a conditional clear-button suffix. Searches across `title`, `code`, and `language` fields, case-insensitive. The query is derived from `_searchController.text.trim().toLowerCase()` on each `setState`.
- **Language filter:** A `PopupMenuButton<String?>` displaying a `Chip` child with the active filter label (or "All languages" when null). The language list is derived dynamically from the current snippet collection (`snippets.map((s) => s.language).toSet().toList()..sort()`). Selecting a language filters the list; selecting "All languages" clears the filter.
- **Sort:** A `PopupMenuButton<SnippetSort>` with three modes:
  - `recentlyUpdated` — descending `updatedAt`, tie-breaker `a.id.compareTo(b.id)`
  - `recentlyCreated` — descending `createdAt`, same tie-breaker
  - `titleAZ` — ascending case-insensitive title, same tie-breaker
- **Active filters indicator:** When any filter is active, a row displays `"X of Y"` (filtered count vs total) with a "Clear all" button that resets both search and language filter.
- **No-match state:** When filters produce zero results but the collection is non-empty, a distinct `WtEmptyState` with `Icons.search_off_rounded` and the message "Try adjusting your search or filters." This is visually and semantically distinct from the "No snippets yet" empty state.

### 3.2 How It Was Implemented

- **Pipeline architecture:** The build method applies a three-stage pipeline: `_applySearchAndFilter(snippets, query)` → `_applySort(filtered)`. Language filtering runs first (equality check), then search (substring match across three fields). Sort operates on a defensive copy (`List<Snippet>.of(snippets)`) to guarantee no mutation of the provider's persisted records.
- **State locality:** All discovery state (`_searchController`, `_languageFilter`, `_sort`) is held in `_SnippetsScreenState`. This matches the pattern established by `tasks_screen.dart` and avoids introducing global state for what is purely a presentation concern.
- **`SnippetSort` enum:** Defined in `snippets_screen.dart` alongside the screen that consumes it. No need to promote it to the domain layer.

### 3.3 Problems Faced and Mitigations

| Problem | Root Cause | Mitigation |
|---------|-----------|------------|
| **14px RenderFlex overflow at 320×480** | `DropdownButtonFormField`'s internal `InputDecorator` enforces minimum horizontal constraints that exceed the available width after padding at 320px viewport | **Replaced `DropdownButtonFormField` with `PopupMenuButton<String?>`** using a `Chip` child. The `PopupMenuButton` has no internal minimum-width constraint. This was the definitive fix after three failed attempts (see below). |
| Overflow fix attempt 1 failed | Reduced filter row padding from 16→8px. Overflow persisted at exactly 14px. | The padding was not the source. The `DropdownButtonFormField`'s internal layout was. |
| Overflow fix attempt 2 failed | Replaced `DropdownButtonFormField` with `PopupMenuButton`+`Chip` in the filter row. Overflow persisted at 14px. | The filter row was not the source either — the `DropdownButtonFormField` had already been replaced, but the overflow was still reported. Investigation continued. |
| Overflow fix attempt 3 failed | Reduced all horizontal paddings to 8px across the entire screen. Overflow still 14px. | Confirmed the overflow source was not padding-related. |
| Diagnostic test inconclusive | String interpolation bug (`${d.toString()}` printed literally instead of expanding) in the `FlutterError.onError` handler | Rewrote diagnostic with proper escaping; ultimately the render-tree walk approach also failed due to PowerShell `$` vs Dart `$` collision in the script template. |
| **Final root cause identification** | Systematic extraction of all 4 `Row` widgets from `snippets_screen.dart` revealed the `DropdownButtonFormField` (L96–124) as the only widget with complex internal layout constraints. The `Chip` in the card (L589) was also suspected but ruled out when replacing it with a `Container` did not change the overflow. | The `DropdownButtonFormField` replacement (attempt 2 above) had actually fixed the overflow, but the test was still failing because the `ListView.builder` is lazy and no list items were rendered at 320×480 — the `find.text(...)` assertion failed with "Found 0 widgets", masking the fact that the overflow was gone. |
| Layout test assertion failed after overflow fix | `ListView.builder` doesn't build items until they're scrolled into view. At 320×480, the viewport is too small to render any cards on first pump. | Changed assertion from `find.text('Snippet 0...')` to `find.byType(ListView)` + `find.byIcon(Icons.edit_outlined)` to verify the list rendered without requiring specific items to be visible. |
| `scrollUntilVisible` threw "Too many elements" | The finder matched multiple widgets (the title text appeared in both the card and potentially the detail dialog). | Simplified to type-based and icon-based assertions instead of text-based. |

**Key lesson:** The overflow debugging consumed significant effort because the error message ("14 pixels on the right") did not identify the specific widget. The systematic approach — extracting all `Row` widgets, analyzing their children's constraints, and replacing suspects one at a time — was the correct methodology. The misleading aspect was that the overflow was fixed earlier than realized, but a secondary test failure (lazy list rendering) masked the success.

### 4.2 Migration Safety

The `AppDatabase` schema is at version 2. The `MigrationStrategy.onUpgrade` handler checks `if (from < 2)` and calls `m.createTable(snippets)`. This ensures:
- Fresh installs get both tables via `onCreate: m.createAll()`.
- Upgrades from v1 (Task-only) add the snippets table without touching existing task data.
- The migration was previously verified in S2.4 with dedicated integration tests.

### 4.3 Capability Boundaries

A code-level audit confirmed complete isolation:
- `DriftSnippetRepository` contains zero references to tasks or the tasks table.
- `TaskRepositoryImpl` contains zero references to snippets or the snippets table.
- `snippetListProvider` contains zero references to task providers.
- `SnippetsScreen` contains zero references to task providers or `TasksScreen`.

The two capabilities share only the `AppDatabase` instance (via `databaseProvider`) and the `AppShell` navigation scaffold. This is the intended architecture per DEC-011.

## 5. Cross-Cutting Issues (S2.1–S2.7)

### 5.1 Encoding Issues (Resolved During S2.5)

Several documentation files suffered from two encoding problems inherited from earlier sprints:
1. **UTF-8 BOM** added by PowerShell 5.1's `Set-Content -Encoding UTF8`. Fixed by using `[System.IO.File]::WriteAllText()` with `New-Object System.Text.UTF8Encoding($false)`.
2. **Mojibake** (double-encoded UTF-8 interpreted as Windows-1252) in 5 markdown files. Fixed via a Dart script implementing a manual Win1252 0x80–0x9F mapping and targeted string replacement with exact mojibake sequences built from `[char]0xNNNN` code points.

### 5.2 PowerShell 5.1 Constraints

PowerShell 5.1 cannot represent non-ASCII characters in script source and adds BOM to UTF-8 output. All file writes throughout Phase 2 use the pattern:
```powershell
$utf8NoBom = New-Object System.Text.UTF8Encoding($false)
[System.IO.File]::WriteAllText($path, $content, $utf8NoBom)
```
Dart scripts are used for any file content containing non-ASCII characters, with the Dart source itself kept ASCII-only.

## 7. Known Limitations

1. **Debug APK only.** Release/profile builds require signing configuration not yet set up.
2. **No integration tests.** Widget tests cover UI flows but not full app lifecycle or database persistence across restarts.
3. **No performance benchmarking.** `ListView.builder` provides virtualization, but the collection has not been stress-tested beyond 10 items.
4. **In-memory search.** Acceptable for local-first usage at expected scale. SQLite FTS would be needed for 10k+ snippets.
5. **No undo/redo.** Delete is permanent after confirmation.

Phase 2 is complete. The Snippet capability is fully functional alongside the existing Task capability with zero regressions across 130 tests, clean static analysis, and a verified Android debug build.
