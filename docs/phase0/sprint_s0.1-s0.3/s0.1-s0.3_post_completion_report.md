### 5.4 Problems encountered and mitigations

**Problem 5.4.1 — Analyzer flagged `(_, __, ___)` as `unnecessary_underscores`.** Dart 3.12's lint rules now prefer a single `_` for unused parameters even in multi-parameter closures.
**Mitigation:** All occurrences in `errorBuilder: (_, __, ___) => …` were rewritten to `errorBuilder: (_, _, _) => …`. Re-ran `flutter analyze` → 0 issues.

**Problem 5.4.2 — `flutter create` default `flutter.assets:` was not present.** New Flutter templates omit the `assets:` section until explicitly needed, and simply uncommenting the example comment block would not have registered the images directory.
**Mitigation:** `pubspec.yaml` was fully rewritten (not line-patched) with the `flutter.assets: - assets/images/` entry explicitly declared. `flutter pub get` re-run; asset bundling confirmed by observing the logo rendering on the device.

**Problem 5.4.3 — Em-dash text corruption on the device.** The shell string `'Tasks, snippets, and continuity — all on your device.'` appeared on the physical device as `Tasks, snippets, and continuity â€" all on your device.` The same corruption appeared in the version footer (`v0.1.0 â€" Foundation`). This was *not* a theme/UI bug; it was a text-encoding mismatch between the PowerShell-written source file and the Dart compiler's interpretation.

**Root cause:** PowerShell 5.1's `Set-Content -Encoding UTF8` writes a UTF-8 **BOM** at the file head and encodes multi-byte characters correctly, but when the here-string source contained a literal em-dash (`U+2014`, 3 bytes in UTF-8), the combination of BOM handling + Dart source-file encoding interpretation produced the classic UTF-8-read-as-latin1 artifact `â€"` at compile time.

**Mitigation:** A surgical regex pass over `app_shell.dart` replaced every em-dash (` — `) and en-dash (` – `) with a plain ASCII hyphen (` - `). The file was rewritten with `-Encoding UTF8 -NoNewline` (also to avoid trailing-newline drift). After rebuild, the device displayed clean text. The lesson has been recorded as a convention: **only ASCII characters in Dart string literals written from PowerShell.** Any genuine typographic refinement should happen inside the IDE where the editor's UTF-8 handling is predictable.

**Problem 5.4.4 — Device launch verification gate.** The brief treats "APK built" and "app runs on device" as separate gates. Both must be passed independently.
**Mitigation and evidence:** After the 154 MB APK was built, it was installed on a physical Android 15 device and launched. The resulting screen shows:

- The custom Worktrace logo in both the AppBar (small, 28 px) and the hero section (large, 80 px).
- The system-chosen dark theme rendering with correct contrast: pure black background (`#121212`), white primary text, muted secondary text, and the branded teal-green secondary color on the Snippets icon.
- Correct card outlines using `AppColors.darkBorder`.
- Both "Soon" chips rendering with correct typography and spacing.
- Correct safe-area insets around the Android 15 notch/status bar and the gesture-nav indicator at the bottom.
- Correct status-bar foreground brightness.

The screenshot is retained as the device-launch evidence for both S0.2 and S0.3.

**Problem 5.4.5 — Launcher icon limitations.** Simply copying `WorkTrace.png` as `ic_launcher.png` into every mipmap folder is a pragmatic shortcut, not a proper adaptive-icon pipeline. The source PNG is not pre-scaled to each density's target pixel size (48/72/96/144/192 px), and Android 8+ adaptive icon foreground/background separation is not configured.
**Mitigation:** Accepted as a known limitation for Phase 0 and documented in `design_system.md`. A proper `flutter_launcher_icons` pipeline (or hand-generated adaptive icon pack) is deferred to a later sprint when visual polish is the sprint theme. The current icon is functionally correct — the app has Worktrace's actual brand on the home screen — just not optimally rasterized.

All S0.3 exit criteria are satisfied, including the critical physical-device launch and dark-theme coherence test. The design system is small, usable, and documented. The visual identity is real (owner's actual logo, not a placeholder). The limitations are honest and recorded.
